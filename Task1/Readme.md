# Пояснительная записка: Технологическая архитектура InsureTech (To-Be)

## 1. Доступность и масштабирование

С учётом требований к доступности на уровне **99.9%** и геораспределённого характера системы, предлагается развернуть инфраструктуру в **трёх независимых зонах доступности (AZ)**, расположенных в разных регионах.

Для обработки переменной нагрузки на уровне приложений используется механизм **Horizontal Pod Autoscaler (HPA)** в Kubernetes-кластерах. Это позволит:

* динамически масштабировать количество подов,
* эффективно обрабатывать всплески трафика,
* минимизировать риск деградации сервиса при росте нагрузки.

---

## 2. Межзональная отказоустойчивость и маршрутизация

### 2.1 Изоляция кластеров

Каждая зона доступности разворачивается как **независимый Kubernetes-кластер**.
Это снижает:

* зависимость от межзональной сетевой связности,
* риск каскадных отказов между регионами.

---

### 2.2 Глобальная балансировка трафика

Для распределения пользовательского трафика применяется **GSLB (Global Server Load Balancing)**, обеспечивающий:

* маршрутизацию на основе геолокации клиента,
* учёт состояния зон доступности,
* гибкую политику балансировки (latency-based / health-based routing).

---

### 2.3 Стратегия отказоустойчивости

Выбрана модель **Active-Active**:

* все зоны одновременно обрабатывают пользовательский трафик,
* отсутствует "холодный" резерв,
* при отказе одной зоны трафик автоматически перераспределяется без значительной задержки.

Это обеспечивает:

* минимальный RTO,
* равномерную утилизацию ресурсов,
* высокую общую доступность системы.

---

## 3. Слой хранения данных

Для обеспечения отказоустойчивости данных используется **мультизональная репликация PostgreSQL**:

* Оркестрация кластера: **Patroni**
* Хранилище конфигурации и лидер-элекции: **etcd**
* Тип репликации: **streaming replication**

Дополнительно:

* Резервное копирование: **pgBackRest** (с учётом требований по RPO)

Такая конфигурация обеспечивает:

* автоматический failover,
* согласованность данных,
* управляемое восстановление после сбоев.

---

## 4. Стратегия масштабирования данных

На текущем этапе внедрение **шардирования** представляется преждевременным, поскольку:

* объём данных относительно невелик,
* отсутствует выраженный нелинейный рост нагрузки на хранилище.

Рекомендуемый подход:

* **декомпозиция данных по сервисам (database per service)**,
* независимое масштабирование БД по мере роста отдельных доменов.

Это упрощает:

* эксплуатацию,
* эволюцию схем данных,
* управление нагрузкой.

---

## 5. Использование CDN

Для повышения производительности и снижения задержек предлагается внедрение **Content Delivery Network (CDN)**:

### Основные задачи CDN:

* кэширование статического контента (JS, CSS, изображения),
* ускорение доставки контента за счёт edge-узлов,
* снижение нагрузки на backend-инфраструктуру,
* защита от DDoS и всплесков трафика.

### Эффекты от внедрения:

* уменьшение latency для пользователей из разных регионов,
* снижение нагрузки на GSLB и origin-серверы,
* повышение общей устойчивости системы к пиковым нагрузкам.

### Рекомендуемый подход:

* использовать CDN как первый слой перед GSLB,
* настроить кэширование с учётом TTL и инвалидации,
* для динамического контента — применять selective caching или bypass.
